# R6: rol de sesión dedicado a Cartera — diseño corregido

Preparación aislada. No está instalado ni cambia cuentas, Auth, saldos o permisos productivos. Se mantiene R5 sin editar hasta revisar este diseño y el delta concreto.

## Límite verificable de la sesión

La cuenta individual de aplicación operador_cartera recibiría el rol JWT/SQL kora_cartera_session mediante Auth admin desde servidor, por UUID. No hay hook global. El SDK declara ese campo; la prueba aislada con GoTrue y PostgREST oficiales verifica su efecto real. No se añade este rol a ninguna configuración de administradores de Auth.

El rol cliente es NOLOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION y NOBYPASSRLS. No es miembro, heredero ni puede asumir ningún otro rol. Se comprueba MEMBER, USAGE y SET contra cada rol, excluyendo la identidad consigo misma. Solo authenticator obtiene SET TRUE, INHERIT FALSE, ADMIN FALSE. El instalador postgres conserva exactamente la membresía automática de creador: ADMIN TRUE, INHERIT FALSE, SET FALSE, grantor bootstrap superuser (OID 10 verificado). Se exige createrole_self_grant vacío antes de crear. Esa fila no permite al cliente asumir postgres y forma parte del fingerprint. PostgreSQL 17 no permite al creador no-superusuario retirar la concesión de bootstrap; no se intentará quitarla para pasar una prueba. Se exige PostgreSQL >=16. El ejecutor kora_cartera_operator permanece separado y no se concede su membresía al cliente, authenticator ni servicios. El grant previo de administración/SET del instalador al ejecutor se conserva exactamente como R5.

Se fija statement_timeout no mayor que authenticated y un lock_timeout finito compatible. Se comprueban pg_db_role_setting, el rol authenticator y su configuración de PostgREST. No se concede USAGE al cliente en kora_cartera_policy ni auth/kora_private/storage/realtime. El pre-request existente es SECURITY DEFINER y comprueba el contexto cliente sin dar acceso al esquema privado. El cliente solo recibe USAGE public y EXECUTE explícito sobre los cuatro RPC. Cada RPC conserva dueño ejecutor, search_path vacío y SQL fijo. El delta revoca primero EXECUTE de PUBLIC, anon, authenticated y service_role para neutralizar los default ACL de Supabase; después concede exactamente la matriz. Se compara proacl completo normalizado con dueño/grantor esperados, además de privilegios efectivos y membresías.

Matriz EXECUTE final (estrecha el candidato R5 aún no instalado, no quita acceso existente de producción):

| RPC | cliente | authenticated | anon | PUBLIC | service_role | ejecutor dueño |
|---|---|---|---|---|---|---|
| cartera_operador_inicio() | sí | sí | no | no | no | sí por dueño |
| cartera_operador_datos(text,date,uuid,uuid,integer,integer,uuid) | sí | no | no | no | no | sí por dueño |
| cartera_operador_guardar_gestion(uuid,uuid,text,text,text,date,numeric) | sí | no | no | no | no | sí por dueño |

La sesión authenticated de una identidad alguna vez registrada se deniega dentro del arranque, incluso desactivada o con perfil cambiado. El arranque solo devuelve restricted:false a usuarios ordinarios nunca registrados. No se amplían grants a roles existentes.

## Aclaración C1: permisos PUBLIC y frontera HTTP

NOINHERIT no elimina PUBLIC. No es posible retirar a un solo rol un permiso concedido a PUBLIC; hacerlo globalmente rompería los demás usuarios y excedería el alcance. Por tanto no se afirma que el rol tenga únicamente cuatro funciones SQL ejecutables. Puede heredar funciones PUBLIC existentes y funciones de catálogo. La garantía propuesta es más precisa: rol NOLOGIN sin SQL arbitrario, sin acceso efectivo a datos ni rutinas que eludan ese límite; cuatro rutas RPC de negocio mediante PostgREST y un conjunto residual de invoker inocuos, enumerados y fijados. Este límite necesita aprobación expresa del diseño; si no resulta suficiente no se instala y no se modifican ACL globales para aparentar cumplimiento.

Se inventarían y fijarían por hash los permisos PUBLIC ya existentes de esquemas, rutinas y default ACL de los esquemas alcanzables (incluidos public, extensions y catálogos). Se documentan CONNECT/TEMP de PUBLIC. Ninguna nueva concesión a PUBLIC se acepta automáticamente. Se excluyen objetos temporales de otra sesión de la huella, no se usa esa exclusión para omitir esquemas persistentes. Las funciones residuales PUBLIC de aplicación solo pueden ser invoker sin efectos fuera de sus privilegios SQL. Una función SECURITY DEFINER, de red, archivo, dblink, NOTIFY o efectos externos en cualquier esquema alcanzable bloquea activación; el pre-request no basta para aceptarla. Las funciones trigger/internal no invocables como RPC se inventarían por separado y no se tratan como lecturas de datos disponibles. Cualquier corrección per-object fuera de Cartera necesitaría alcance y revisión propios; no está autorizada aquí. Las rutinas propias de este delta revocan PUBLIC por objeto y fijan grants explícitos. El alias de identidad R5 cartera_subject() se estrecha también: se concede exactamente a anon, authenticated, service_role y kora_cartera_operator; postgres conserva sus derechos de dueño. kora_cartera_session NO recibe EXECUTE directo: los RPC lo usan con privilegios del ejecutor. El delta compara los consumidores previos de las seis dependencias y bloquea si existe algún rol adicional que esta lista dejara sin acceso; no lo agrega automáticamente. No hay excepción de rutina propia PUBLIC por conveniencia. Se prueban llamadas directas a funciones ficticias PUBLIC SECURITY DEFINER que darían datos si se eludiera el pre-request, incluso POST/GET, métodos, Accept/perfiles y variantes de ruta; deben dar error sin efectos. No se autoriza GraphQL ni SQL arbitrario. Toda ruta no prevista, representación plan, root/OpenAPI, HEAD, OPTIONS autenticado y cambio de esquema sigue bajo los gates existentes. CORS/OPTIONS sin SQL no queda certificado por una prueba SQL.

Para relaciones, vistas, matviews, foreign tables, columnas y secuencias no se acepta NINGÚN privilegio efectivo del cliente, ni propiedad, ni pertenencia a roles con acceso, en esquemas persistentes de aplicación/proveedor. Los catálogos PostgreSQL de metadatos son un baseline explícito, no datos empresariales. Un grant de datos a PUBLIC también bloquea. Las rutinas SECURITY DEFINER de storage/realtime ejecutables por PUBLIC/cliente bloquean; las funciones de esos esquemas se fijan por definición/ACL/dueño/search_path. Si otro backend permite ejecutar funciones PUBLIC sin el pre-request, ese backend debe negar el rol dedicado o queda bloqueada la activación.

## Compatibilidad administrada sin alterar sus tablas

Las 13 relaciones autorizadas se inventarían exactamente. El control del nuevo cliente exige cero USAGE/CREATE en storage/realtime y cero permisos efectivos de relación/columna/secuencia, sin propiedad ni membresías. Ya no exige RLS a las tablas de control para authenticated: la ausencia de RLS no es un fallo cuando el cliente carece de acceso. No se cambia RLS, dueño, grants ni se crean nuevas políticas para el nuevo cliente en objetos administrados. No se ejecuta SQL de escritura en las dos tablas de control.

Las políticas R5 para JWT authenticated de identidades históricamente registradas siguen siendo una propuesta independiente, aún no instalada; no se da por autorizada nueva política del proveedor ni se confunde con las constantes FALSE del cliente. Sin esas defensas de tokens previos, la transición solo es posible tras bloqueo, revocación y vencimiento comprobado de TODOS los JWT antiguos. Para prevenir un downgrade posterior, la auditoría servidor rol Auth/registro y los gates de Storage/Realtime son obligatorios. Un fallo impide activar, nunca amplía authenticated ni resetea su rol para desbloquear.

Se mantienen restrictive FALSE solo en tablas de aplicación públicas si están en el delta revisado. Nunca se usan para alterar acceso de otros roles. Sus ACL y políticas previas deben permanecer idénticas. No se reemplaza ni se desactiva la confirmación diaria de deuda de otros usuarios.

El pre-request ES un cambio global del cuerpo de public.kora_confirmacion_deuda_pre_request(), ya previsto en R5 y sujeto a revisión del delta R6. Su configuración está en pgrst.db_pre_request del rol authenticator; se verifica sin cambiarla. La función conserva exactamente su dueño/ACL de producción y agrega solo el nuevo rol al EXECUTE necesario. Antes/después se comparan anon, authenticated y service_role, roles de tienda/auditoría/gerencia y confirmación diaria pendiente/confirmada. El cuerpo original para sesiones ordinarias se conserva byte a byte donde sea posible. Directamente llamar el guard no devuelve datos ni produce cambios; para el rol dedicado, su propia ruta se rechaza por no estar en la lista.

El guard SECURITY DEFINER comprueba SQL role y claim incluso dentro de definers. Para cada valor ausente se usa IS DISTINCT FROM; se rechaza la ausencia de método/path/claims. Pin de esquema public mediante Accept-Profile y Content-Profile, JSON solamente y sin tx=rollback/params alternos. Exactamente un overload por cada nombre permitido en TODOS los esquemas expuestos y retorno escalar jsonb, nunca SETOF/composite, evita usar computed fields/embedding para llamar otra rutina. El gate enumera argumentos/defaults y compara prorettype/proretset por OID. Se ensayan filtros/select/order, Prefer params/tx, case, barra final/doble y percent-encoding; no se deduce la ruta decodificada de un test SQL.

La defensa de relación es independiente de la guardia: una segunda instancia PostgREST local sin pre-request debe negar tablas por privilegios. Una función PUBLIC SECURITY DEFINER ficticia debe poder ejecutar allí y quedar bloqueada con guardia, demostrando por qué NO se admite ese residuo en el candidato real. Las denegaciones con guardia comprueban código y mensaje exacto, no solo HTTP 401/403. El gate real prueba root/OpenAPI, GET, HEAD y recarga de caché en la versión alojada, y sigue bloqueando si la versión difiere sin repetición.

El interruptor de bloqueo es REVOKE kora_cartera_session FROM authenticator GRANTED BY postgres (con grantor exacto verificado): elimina el acceso de ese rol sin devolver a nadie a authenticated. El procedimiento lo prepara revisado pero NO lo ejecuta en esta preparación. Ningún marcador de GUC se trata como secreto; los cuatro RPC comparan identidad/contexto por sí mismos y el fingerprint permanece obligatorio.

## Identidad y huella

Se compara exactamente current_setting('role',true), fijado por PostgREST para la transacción, con request.jwt.claims.role firmado. current_user dentro de DEFINER es el ejecutor y no sirve de identidad. Se rechaza is_anonymous=true, sub vacío/ajeno, cuenta inactiva/no registrada, rol inválido, diferente en mayúsculas/espacios, inexistente o downgrade authenticated para sub registrado. No se confía en user_metadata ni en el cuerpo. Se ensaya con conexión authenticator y SET LOCAL ROLE, además del API real local.

El fingerprint y comprobación repetible de activación incorporan atributos y membresías de cliente/ejecutor/authenticator; configuraciones de rol y base; esquemas; todos los default ACL; definiciones, EXECUTE, proowner, prosecdef, proconfig de las rutinas alcanzables; relaciones, columnas, secuencias, políticas, triggers, dependencias y metadatos de las 13 tablas. Se comprueba antes de sellar y al activar contra el hash revisado, sin resello automático. Los cambios del proveedor, incluidas particiones, siguen bloqueando hasta revisión.

## Integridad Auth, transición y retirada

Pruebas locales oficiales: emisión inicial, refresh, cambio de contraseña, cambio de email confirmado por administrador, sin correo, nuevo login y self-update malicioso no cambian el rol confiable; la cuenta ordinaria conserva authenticated. No se simula el efecto solo firmando JWT a mano. Tokens firmados manualmente se usan para el administrador del fixture local service_role y para pruebas negativas de rol, siempre con secreto local ficticio. No se usa una clave de servicio real.

Antes de cualquier activación real se auditan sin exportar identidades: todo usuario con rol dedicado pertenece al registro activo; todo registro activo tiene rol dedicado; ningún hook/herramienta sobrescribe el rol y ningún consumidor interpreta un rol desconocido como privilegiado. Se auditan ramas role===authenticated, role!==anon y session.user.role del cliente y los dos backends. El fixture incluye logout global, rechazo de refresh revocado, lectura admin del rol después del intento de self-update y cambios de credenciales, y valores reales de statement_timeout/lock_timeout dentro del RPC PostgREST: SET ROLE por sí solo no aplica ALTER ROLE SET. Se añaden pruebas ficticias.

Transición individual ordenada: verificar UUID autorizado; bloquear inicio; revocar refresh/sesiones; esperar máximo vencimiento de access tokens previos más la tolerancia documentada de 30 segundos de PostgREST y margen operativo adicional (no asumir que revoke mata JWT); cambiar rol desde servidor; levantar bloqueo; nuevo login; comprobar rol/alcance desde servidor. No se selecciona una cuenta en esta preparación. Si se desactiva o recupera, se desactiva contrato/cuenta y revocan sesiones manteniendo registro sticky; nunca se vuelve a authenticated como medio de abrir el ERP. Cualquier reversión del rol exige mantener el bloqueo y las restricciones y una revisión independiente; no es rollback automático.

## Comprobaciones continuas previstas, deshabilitadas hasta revisión

El código del monitor servidor se debe preparar y revisar junto al delta; no se crea ahora ninguna automatización ni se guarda una credencial privilegiada. Su contrato es ejecutar cada 60 segundos y después de cada migración/actualización de Auth: correspondencia rol/registro (a/b), configuración pre-request/rol, membresías y el inventario de rutinas alcanzables. Un fallo aplica el interruptor revisado y alerta sin incluir identidades en logs públicos; su ausencia/antigüedad bloquea activación y renovación operativa. Todos los cambios de catálogo futuros deben comprobar cobertura y C1' DENTRO de la transacción antes de confirmar: un monitor periódico no promete impedir una ventana por DDL administrativo que se salte ese proceso.

Las políticas de aplicación R5 para todo sub históricamente registrado bajo authenticated son prerrequisito, no una opción. No resuelven por sí solas los controles administrados sin RLS: el interruptor del rol dedicado tampoco bloquea un JWT que fue degradado a authenticated. Ese límite se reconoce expresamente. NO se acepta ese riesgo residual en este diseño: la activación permanece bloqueada hasta demostrar en las superficies reales que esos controles son inaccesibles a ese JWT, o hasta aprobar una solución específica independiente. No se cambia RLS del proveedor ni se toma la falta de exposición REST como prueba de Realtime/Storage. Auditoría y espera de tokens solos no certifican esa denegación.

## Gates que siguen abiertos

Storage, Realtime (incluidos Broadcast/Presence públicos y caché), GraphQL, enlaces firmados anteriores, dos backends y límites externos deben negar el nuevo rol sin fallback privilegiado. Las conexiones de servicio no reciben membresía del rol. La prueba PostgREST local no certifica esos servicios ni Supabase alojado. No se habilita ningún perfil real antes de pasar esos gates y el esquema completo compatible.

R6 sigue siendo un diseño de preparación, no aprobación para instalar, asignar usuarios o publicar. El código R5 y sus 39 pruebas conservan su aprobación anterior solo dentro de su alcance original; este diseño no hereda esa aprobación para cambios nuevos.


## Fuentes primarias y evidencias técnicas

- PostgreSQL 17, Role Attributes: concesión automática ADMIN TRUE, INHERIT FALSE, SET FALSE del bootstrap al creador no-superusuario; no puede revocarla el propio creador: https://www.postgresql.org/docs/17/role-attributes.html .
- PostgREST 16 y 14, Authentication: exp/iat/nbf admiten 30 segundos de clock skew: https://docs.postgrest.org/en/stable/references/auth.html y https://docs.postgrest.org/en/v14/references/auth.html .
- Los resultados locales no se suman a las 39 pruebas R5 ni certifican el proveedor. Cada ejecución guarda resultado y digest de imagen; los intentos fallidos se conservan y no se transforman en aprobaciones.


## Definición precisa de superficie H/S y excepción de guardia

- Tier H (invocable HTTP): TODAS las rutinas de TODOS los esquemas expuestos por cualquier configuración PostgREST/GraphQL que pueda asumir el rol. Incluye perfiles alternos, no solo el predeterminado. La prohibición de PUBLIC SECURITY DEFINER y efectos externos se aplica aquí; excepciones exactas: los cuatro RPC propios (PUBLIC revocado) y public.kora_confirmacion_deuda_pre_request() como guardia existente. Su proacl/dueño se fijan exactamente en el fingerprint; si ya tuviera PUBLIC EXECUTE, agregar al cliente no ampliaría el acceso efectivo y no se cambia ese ACL sin revisión. Directamente invocada no abre una ruta de negocio ni altera datos.
- Tier S (alcanzable SQL sin ruta HTTP): pg_catalog, information_schema y esquemas con USAGE que no estén expuestos. Sus funciones de sistema, incluidos set_config/pg_notify/locks/sleep/large objects, son baseline explícito, no bloqueos imposibles de satisfacer. No se revoca PUBLIC globalmente. Se enumera el callgraph de los cuatro RPC/guardia con pg_depend más revisión de cuerpos PL/pgSQL (pg_depend no cubre todas sus llamadas); solo se permiten llamadas S expresamente revisadas. Ningún input selecciona SQL ni función. Una nueva llamada o cambio de definición/ACL/configuración bloquea; pasar un esquema S a exposición H obliga a reclasificar antes de confirmar el cambio.
- Los controles de relaciones de datos y funciones de Tier H prevalecen sobre cualquier frase previa que use genéricamente “alcanzable”. No se usa esta distinción para esconder un camino por otro backend: los servicios que conecten como authenticator o un miembro del rol también se inventarían y deben negar datos sin depender de pre-request.

## Evidencias y alcance del fixture final

La prueba crea el cliente a través de postgres sin superusuario y con CREATEROLE; verifica el self-grant vacío y la fila de bootstrap ADMIN TRUE/INHERIT FALSE/SET FALSE. Se comprueban atributos, ausencia de membresías hacia delante, las dos filas inversas exactas, ajustes de rol y la versión. Registra el intento fallido de retirar el grant de bootstrap. El inventario H identifica qa_public_leak como definer inseguro bloqueante y qa_subject como invoker PUBLIC residual (exclusivamente del fixture, sin copiar ese grant al candidato real).

POST/GET a PUBLIC y GET root exigen HTTP 403, code PT403 y message qa_session_route_denied; HEAD exige 403 y cero efectos. No se acepta JWT 401 como prueba de guardia. Si una versión omite el guard para root queda gate abierto, no aprobación. NOTIFY de recarga seguido de RPC permitido y denegación exacta se ensaya localmente. Se prueba el interruptor con GRANTED BY postgres: token dedicado da 42501 por imposibilidad de asumir su rol y el usuario ordinario sigue leyendo. La autenticación anónima de un RPC ficticio ordinario pasa la guardia y permite detectar errores de casteo de claims vacíos.

La prueba de email es la ruta administrativa confirmada, NO el flujo self-service de verificación de correo. Ese flujo sigue siendo prerrequisito antes de habilitar cambios de email para una cuenta real de Cartera. No se envían correos en el fixture. El SHA del script se calcula dentro del propio script al producir el resultado; no se agrega a posteriori como si lo hubiera medido la ejecución. Se reportan el total de assertions y nombres distintos, sin sumarlos a las pruebas de R5 ni confundir repeticiones de login con propiedades independientes.


## Alcance final de dos assertions, según revisión R4

Las peticiones posteriores a NOTIFY muestran éxito/denegación después de enviar la notificación, pero NO acreditan que el cache haya recargado; no se observó un sentinel. Las tres sondas de rol inválido muestran rechazo HTTP, pero ese endpoint también rechazaría un fallback sin EXECUTE, de modo que NO acreditan ausencia de fallback. El interruptor sí acredita ausencia de fallback con 42501 y el nombre del rol que no pudo asumirse. Estos límites no se convierten en aprobaciones de integración o proveedor.


## Delta de implementación: relaciones de extensiones del sistema en Tier S

La denegación SQL de datos cubre todas las relaciones de aplicación, los seis esquemas protegidos y cualquier relación persistente que no sea miembro de una extensión PostgreSQL. Para un objeto que pg_depend vincula a una extensión (deptype=e, refclass pg_extension), fuera de los esquemas protegidos y fuera de las rutas HTTP permitidas, los grants PUBLIC preexistentes se tratan como baseline Tier S, del mismo modo que sus funciones de sistema. No se revocan para otros usuarios. No se concede ninguno al nuevo rol. Todos sus ACL/columnas/definiciones/políticas y la versión de la extensión quedan incluidos en la huella: un cambio cierra los RPC. No se considera una excepción para objetos de aplicación ni para Storage/Realtime/Auth/Cartera aunque pertenezcan a una extensión.

Esta excepción requiere demostrar que los esquemas S no están expuestos a la cuenta mediante HTTP y que ningún cuerpo o trigger de los cuatro RPC lleva a sus datos o funciones externas. Las cuatro respuestas son JSON escalar y no admiten SQL o nombres de funciones/tablas procedentes de inputs. La revisión del delta debe aceptar este límite explícito; la aprobación anterior de diseño no se presenta como aprobación automática de este cambio. No se comparte inventario productivo adicional: los tests usan objetos de extensión de la imagen oficial o ejemplos ficticios, nunca registros.
