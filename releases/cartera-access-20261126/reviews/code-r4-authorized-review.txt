## D1: Managed inventory and isolation

**What I verified:**
- **Exact inventory:** The inventory covers `r,p,v,m,f` in `storage`/`realtime`. The SQL ordering matches the baseline ordering under C collation. For example, `bucket_lifecycle_states` sorts before `buckets`, and `s3_*` sorts before `vector_indexes`.
- **Same check in every path:** `scope-core.sql`, `scope-full.sql` and `cartera_assert_managed()` all use it. The preflight is a nested PL/pgSQL `declare … begin … end;` block. Its shadowing of `expected`/`actual` is valid and scoped.
- **Seal coverage:** The fingerprint now covers every relation in both schemas.
- **Policy predicate:** The check `r=0 or pg_has_role('authenticated',r,'USAGE')` has the right semantics.
  - `USAGE` corresponds to `has_privs_of_role`, which is what RLS uses to decide whether a policy applies.
  - It is correct under NOINHERIT roles and PG16 per-grant `inherit` options.
  - `pg_has_role` with OID 0 returns false rather than erroring.
- **Provider objects untouched:** No privileges, ownership or RLS on provider objects are modified.
- **Gate mirrors SQL:** The gate's `authenticated_permissive` flag, its kind check and its unexpected-relation handling match the SQL. The managed set comes from the pinned inventory module, not from the snapshot.

**Required fix: test the isolation branch itself.**

The fourth-table test is aborted by `cartera_managed_inventory_changed` before the isolation clause ever runs. As a result, `cartera_managed_surface_not_isolated` and the gate's "managed surface not isolated" error are never exercised. Add fictional cases on an *already inventoried* non-overlay relation, for example `storage.migrations`:

1. A permissive policy `to public`.
2. A permissive policy to a fictional role granted to `authenticated` with `inherit true`.
3. A control case: the same membership with `inherit false`. It should *not* trip, which shows the predicate tracks inheritance correctly.
4. `disable row level security`.

Each case should assert three things:
- Atomic install abort, with no role or `cartera_subject` created.
- `cartera_activate`/`assert_ready` rejection on an installed fixture, with the contract still disabled.
- The integrated `checkPermissionContract` reporting the specific isolation error.

**Required fix: stale runbook sentence.**

`RECUPERACION-Y-PUBLICACION.md` § "Migraciones y publicaciones futuras" still says coverage applies to "cada tabla pública y las tres tablas administradas". Align it with the later paragraph:
- Every public table and the three overlays require the exact deny.

**Document as an activation gate (not a source blocker):**
- **Daily Realtime partitions.** Real Realtime normally creates daily `realtime.messages_*` partitions. None appear in the baseline. Under exact inventory, a partition rotation closes all guarded RPCs, and every RPC runs `assert_ready`. That fails closed, which is consistent with your "deliberate blocking gate". The runbook should still name it explicitly so it is not mistaken for an incident. Accepting partitions requires a separately reviewed design.
- **Managed functions are outside the fingerprint.** These are owner-run `SECURITY DEFINER` functions in `storage`/`realtime`, and they bypass non-forced RLS. They belong to the provider/API behavior gate you already listed.
