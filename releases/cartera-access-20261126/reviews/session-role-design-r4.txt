## Fixture changes required

### F1. The reload assertions do not show that a reload happened

`NOTIFY pgrst,'reload schema'` is asynchronous, and the script only sleeps 0.5 s before testing. Both "survives schema-cache reload" assertions would pass identically if the reload never ran or had not finished, because the requests could be served from the old cache.

**Fix (pick one):**

- **Sentinel.** Before the NOTIFY, create a new fictional function (for example `public.qa_reload_marker()` with no grants to the session role). Poll until PostgREST stops returning 404 / PGRST202 for it, then repeat the allowed RPC and the exact denial.
- **Rename.** Call the assertions "…after NOTIFY (reload completion not verified)".

### F2. The "invalid role claim never falls back" assertions are non-discriminating

The probes target `/rpc/qa_bootstrap`, whose EXECUTE is revoked from anon, authenticated and service_role. A fallback to authenticated or anon would therefore also produce 401 or 403, so `status in (400,401,403)` cannot tell no-fallback from fallback.

**Fix (pick one):**

- **Discriminate.** Send the wrong-role tokens to a route that a fallback role *would* succeed on, such as `/qa_regular` (readable by authenticated) or `/rpc/qa_ordinary` (anon/authenticated). Assert the specific role-assumption error code and message, as the kill-switch test already does.
- **Rename.** Call the assertions "invalid role claim is rejected".

## Non-blocking notes

- **N1. Fixture Tier-H query scope.** The inventory query filters `nspname='public'`, but the fixture exposes `public,realtime`. This is acceptable as the negative test of the gate. The real gate must iterate over every schema in every PostgREST/GraphQL configuration, as the design states. It must also cover side-effecting invoker functions, not only `prosecdef`.
- **N2. Bootstrap revoke attempt.** `REVOKE … GRANTED BY supabase_admin` run as postgres may fail because postgres cannot act as that grantor, not because of a bootstrap-specific rule. The row-persists check is sound, and "cannot revoke" holds either way. Still, capture the SQLSTATE and message privately, and optionally also record the plain `REVOKE` form, which defaults the grantor to postgres and is likely a warning or no-op. The design does not depend on this outcome.
- **N3. Anonymous guard test.** In the fixture guard, the claims cast sits inside the session branch, and PostgREST always sets claims for anon. The anonymous test therefore checks that the guard does not break anon. It does not exercise an empty-GUC cast. The empty-string risk is in RPC bodies that cast without `nullif`, such as `qa_bootstrap`. In the real RPCs, use `nullif(...,'')` there too.
- **N4. Matrix completeness for `postgres`.** Supabase default ACLs typically also grant EXECUTE to `postgres`. The expected normalized `proacl` should state whether a `postgres` (installer) entry is present or revoked, so the exact comparison has a defined target.
- **N5. Guard grant wording.** The sentence "El cliente solo recibe … EXECUTE explícito sobre los cuatro RPC" omits the guard EXECUTE, which the pre-request requires. The Tier-H section covers this, but align the sentence.
- **N6. Assertion name.** "provider control remains readable by original role only" asserts only the first half. The "only" part is shown by separate assertions, so consider renaming it.
