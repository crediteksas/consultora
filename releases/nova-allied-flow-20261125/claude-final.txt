**Non-blocking items for your preflight**
1. **Constraints the fixtures can't show.** The fixtures contain columns only, with no constraints, triggers or indexes. Your metadata preflight should cover:
   - checks or triggers on `enlaces_registro`, especially `token_sufijo` length or format;
   - checks on `captadores` (the `tipo='tercero'` value, and the normalized-name uniqueness implied by `captadores_duplicados_normalizados` at `clientes/index.mjs:4559`);
   - any `store_code` check on Aura `nova_credit_applications`, which the Aura migration doesn't change.

   Any of these would fail closed: the transaction rolls back, or new-store deliveries are refused. None of them would expose data.
2. **Suffix length.** The existing ally provisioning stores a 6-character suffix (`token.slice(-6)`, `clientes/index.mjs:4554`), while the new script stores 8 (`right(v_hash,8)`). It's cosmetic since the suffix is admin-only, but admins will see two different lengths.
3. **Member rows aren't locked.** The member and profile rows are read without `FOR SHARE`, so there is a small gap between the check and the writes. It's negligible because the script only writes to captadores and links.
4. **Search path when applying.** `aura-3` and `aura-6` use the unqualified type `nova_platform_jobs`, so the session that applies the migration needs `public` on its search_path. That's the Supabase default; otherwise the migration fails as a whole.

The rollout order (commit/push, then preflight, then Kora, Aura, the one-off script and both Workers) and the manual rollback with no data deletion are sound as described.
