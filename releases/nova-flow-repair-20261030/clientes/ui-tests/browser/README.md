This runner uses an existing Playwright installation and an installed Google Chrome executable. It does not install dependencies, download a browser, attach to a user's browser, or use CUA.

Example on macOS, using the absolute path of a Playwright `index.mjs` already installed locally:

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/existing/node_modules/playwright/index.mjs \
node releases/nova-flow-repair-20261030/clientes/ui-tests/browser/browser-regression.mjs
```

`CHROME_EXECUTABLE` can override `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`. The runner creates its own `/private/tmp/nova-flow-chrome-*` profile and closes/removes that profile after the tests. The macOS filesystem sandbox denied the initial browser launch before any page loaded; the same authorized local test then ran successfully outside that sandbox. It never used the existing browser profile.

The form is generated by the frozen transform from the pinned baseline. A visible local-test banner and a closed mock bootstrap are added to the test fixture. External asset tags are stripped. Every page request is intercepted; only synthetic document navigation and favicon requests can be fulfilled. External DNS resolution is disabled, service workers are blocked and the document enforces CSP `connect-src 'none'`. `window.fetch` handles a fixed list of fake API routes in memory. All identities and pictures are synthetic. Provider delivery, OCR and storage behavior are mocked.

Four browser scenarios passed in Chrome 156.0.8078.74:

- Expired document uploads, explicit verification using the existing OTP controls, and recovery of the existing source. All three original `File` objects, input nodes and values remain; only the two pending photo types upload.
- Recovery Save disables file inputs and consent. A deliberately forced replacement with B while A's response is held causes the stale A response to be discarded; the later upload contains B.
- With the managed/SMS branch locally enabled, editing a verified identity clears only that terminal challenge. Both explicit send actions become available, all Files remain, and no automatic second send occurs. This does not change or validate the production SMS activation flag.
- Legacy 202 `accepted` allows entry of a received code. Legacy 202 `uncertain` hides code entry and reports that the send is unconfirmed. Neither branch claims delivery and no automatic resend occurs.

`evidence/receipt.json` records the exact candidate SHA, runtime assertions, redacted request paths/counts and six screenshots. `actualApiNetworkRequests`, unexpected requests and page errors are all zero. File identity is proven by strict browser-object equality assertions in the receipt; screenshots illustrate the visible states. These tests establish client behavior against the mocked contract, not provider delivery or production server behavior.
