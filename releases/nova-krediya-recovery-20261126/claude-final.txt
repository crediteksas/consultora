## Blocker: `recoverName` doesn't enforce the "exclusive" checks you described

In `candidate/operational/extension/driver.mjs:48-51`:

1. **It doesn't require a single, exact name prompt.** The check at line 48 is `following.some(...)`, and it accepts either the name prompt **or** the provider's ID-number prompt (`comparteme tu numero de cedula…` / `me indica su numero de cedula`). Other provider messages may also follow, as long as one of them matches. This is the same as the legacy rule; the exclusive proof doesn't tighten it.
   - Example: the provider re-asks for the ID number, or sends some other message within 5 minutes of the document confirmation. The connector would then send the authorized name into the wrong conversation state. The runner should catch it, so no result gets invented, but it's an unnecessary send of personal data.
2. **The exclusive checks only run when the prompt is older than 2 hours.** Line 51 is `now()-at>2*3600000&&!exclusiveHeldPrompt`. When the prompt is under 2 hours old, the journal binding is skipped entirely: request created ≤ document confirmation, the 5-minute prompt window, and the 24-hour cap. Under 2 hours is the normal restart case (lease of about 5 minutes plus the 60-second grace), so the binding is skipped most of the time.

**Fix:** when `proof?.exclusiveResume===true`, require `exclusiveHeldPrompt` whatever the prompt's age. Also require exactly one message after the document, and that it is exactly the name prompt (`me brinda por favor su nombre y apellido`): no ID-number alternative and no extra messages. Add driver tests for:
- the provider re-asking for the ID number;
- a name prompt followed by another provider message;
- an exclusive proof under 2 hours with a prompt outside the window.
